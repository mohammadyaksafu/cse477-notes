    LECTURE 19

    HTTP, DNS ও Email — নেটওয়ার্কের ভিত্তি

    Network security-র আক্রমণগুলো বুঝতে আগে জানতে হবে স্বাভাবিক অবস্থায় জিনিসগুলো কীভাবে চলে: ওয়েব পেজ কীভাবে আসে (HTTP), নাম থেকে IP কীভাবে পাই (DNS), আর ইমেইল কীভাবে যায় (SMTP, POP, IMAP)। পরের লেকচারগুলোর প্রায় সব আক্রমণ এদেরই দুর্বলতা কাজে লাগায়।

    Web ও HTTP

    একটা web page কয়েকটা object দিয়ে তৈরি — HTML ফাইল, JPEG ছবি, Java applet, অডিও… একটা base HTML ফাইল থাকে যা অন্য object-গুলোকে রেফার করে। প্রতিটা object একটা URL দিয়ে চিহ্নিত।

    www.sust.edu/cse/images/logo.png └─ host name ─┘└──── path name ────┘

    HTTP (HyperText Transfer Protocol) একটা application layer protocol, client/server মডেলে চলে:

    • Client = browser — object চায়, পায়, দেখায়।
    • Server = web server — অনুরোধের জবাবে object পাঠায়।

    HTTP কীভাবে চলে

    💻 BrowserTCP SYN → :80🖥️ Server

    ধাপ ১: Client সার্ভারের port 80-এ TCP connection শুরু করে।

    💻 Browser← accept🖥️ Server

    ধাপ ২: Server TCP connection গ্রহণ করে।

    💻 BrowserGET /index.html ⇄ 200 OK🖥️ Server

    ধাপ ৩: HTTP বার্তা (request/response) বিনিময়।

    💻 Browser✂️ close🖥️ Server

    ধাপ ৪: TCP connection বন্ধ।

    🎯 HTTP is stateless

    Server আগের কোনো request-এর তথ্য মনে রাখে না। কেন? State রাখা protocol জটিল — অতীত ইতিহাস রাখতে হয়, আর server/client crash করলে দুজনের “state”-এর ধারণা অসামঞ্জস্যপূর্ণ হয়ে যেতে পারে।

    📖 উপমা

    Stateless সার্ভার যেন এমন দোকানদার যার স্মৃতিশক্তি শূন্য — প্রতিবার গেলে নতুন কাস্টমার ভাবে। “গতকাল যে বাকি নিলাম” — মনে নেই! তাই আমাদের একটা টোকেন (cookie) সাথে নিয়ে যেতে হয়।

    HTTP Request, GET ও POST

    দুই ধরনের HTTP বার্তা: request ও response। Request বার্তা ASCII — মানুষ পড়তে পারে।

    ⚠️ মনে রাখো

    HTTP Response ও Status Code

    HTTP/1.1 200 OK ← status line Date: Sun, 26 Sep 2010 20:09:20 GMT Server: Apache/2.0.52 Content-Type: text/html <html>...requested HTML file...</html>
    তুমি একটা পুরনো লিংকে গেলে, আর browser নিজে থেকেই নতুন ঠিকানায় চলে গেল। Server সম্ভবত কোন code পাঠিয়েছিল?
    301 + Location header → browser redirect করে।

    Cookie: Stateless HTTP-তে State

    অনেক transaction জুড়ে state রাখতে cookie ব্যবহার হয় — HTTP বার্তাই state বহন করে। Cookie দিয়ে: authorization, shopping cart, recommendation, user session state।

    Cookie-র চারটা উপাদান

    1. HTTP response-এ cookie header line (Set-Cookie:)
    2. পরের HTTP request-এ cookie header line (Cookie:)
    3. ব্যবহারকারীর host-এ (browser) রাখা cookie ফাইল
    4. Web site-এর back-end database

    Susan-এর গল্প

    👩 SusanGET /shop →🛒 amazon

    ধাপ ১: Susan প্রথমবার একটা e-commerce সাইটে গেল। তার request-এ কোনো cookie নেই।

    👩 Susan← Set-Cookie: id=1678🛒 amazon
    DB: 1678 → {}

    ধাপ ২: সাইট একটা unique ID (1678) বানায়, backend database-এ এন্ট্রি রাখে, আর response-এ Set-Cookie পাঠায়। Browser cookie ফাইলে সেভ করে।

    👩 SusanCookie: id=1678 →🛒 amazon
    DB: 1678 → {বই}

    ধাপ ৩: পরের প্রতিটা request-এ browser নিজে থেকে Cookie: id=1678 পাঠায়। সাইট ID দেখে database থেকে Susan-এর cart বের করে — cookie-specific action।

    👩 Susan(এক সপ্তাহ পর) Cookie: id=1678 →🛒 “Welcome back!”

    ধাপ ৪: এক সপ্তাহ পরেও একই cookie — সাইট চিনে ফেলে, recommendation দেখায়।

    🔒 সিকিউরিটি দিক

    Cookie-ই যদি পরিচয় হয়, তবে কেউ cookie চুরি করলে সে-ই “Susan” হয়ে যায় → session hijacking (Lecture 24–25)। আর cookie দিয়ে সাইট তোমার অনেক তথ্য জানে → privacy সমস্যা।

    DNS — Domain Name System

    Internet host/router-এর দুটো পরিচয়: IP address (32 bit) — datagram-এর ঠিকানার জন্য, আর নাম (www.yahoo.com) — মানুষের জন্য। এদের মধ্যে mapping করে DNS:

    • অনেক name server-এর hierarchy-তে তৈরি একটা distributed database,
    • নাম resolve করার application-layer protocol,
    • ইন্টারনেটের একটা core function।

    DNS service

    • Hostname → IP translation
    • Host aliasing (একটা জটিল canonical নামের সহজ alias)
    • Mail server aliasing
    • Load distribution — replicated web server: একটা নামের জন্য অনেক IP (যেমন amazon.com)
    🎯 কেন DNS centralised নয়?

    (১) Single point of failure — এক সার্ভার পড়লে পুরো ইন্টারনেট অচল। (২) Traffic volume — সারা বিশ্বের query এক জায়গায় সামলানো অসম্ভব। (এছাড়া দূরত্ব ও maintenance-ও সমস্যা।)

    Hierarchy

    Root DNS servers ┌──────────────┼──────────────┐ com DNS org DNS edu DNS ← TLD servers ┌───┴────┐ │ ┌───┴────┐ yahoo.com amazon.com pbs.org poly.edu umass.edu ← Authoritative servers
    সার্ভারদায়িত্ব
    RootLocal server resolve করতে না পারলে যোগাযোগ করে; mapping না জানলে authoritative সার্ভারের দিকে পাঠায়, mapping ফেরত দেয়
    TLDcom, org, net, edu এবং দেশভিত্তিক uk, fr, ca, jp, bd। (com — Network Solutions; edu — Educause)

    Local (default)Hierarchy-র অংশ নয়; প্রতিটা ISP/ভার্সিটি/কোম্পানির থাকে। Host-এর query প্রথমে এখানে যায়; proxy হিসেবে hierarchy-তে forward করে

    উদাহরণ: me.cs.vt.edu-র host জানতে চায় gaia.cs.umass.edu-র IP।

    🧪 DNS lookup simulator (iterated query)

    দুবার একই নাম খুঁজে দেখো — দ্বিতীয়বার cache থেকে এক ধাপেই উত্তর!

    Caching

    • কোনো name server mapping শিখলে সেটা cache করে রাখে।
    • Cache entry কিছু সময় পর timeout (TTL) হয়ে মুছে যায়।
    • TLD সার্ভারের ঠিকানা সাধারণত local name server-এ cached থাকে → root server-এ খুব কম যেতে হয়।
    • dig ও nslookup দিয়ে DNS-কে সরাসরি প্রশ্ন করা যায়।
    🔒 সিকিউরিটি দিক

    Cache থাকায় একবার ভুল (ভুয়া) উত্তর ঢুকিয়ে দিতে পারলে TTL শেষ না হওয়া পর্যন্ত সবাই ভুল সাইটে যাবে → DNS cache poisoning (Lecture 21)। DNS মূলত authentication ছাড়াই তৈরি।

    Email: SMTP, POP, IMAP

    তিনটা প্রধান উপাদান: user agent, mail server, এবং mail transfer protocol SMTP।

    • User agent (“mail reader”) — মেইল লেখা, সম্পাদনা, পড়া; যেমন Outlook। আসা-যাওয়ার মেইল সার্ভারে থাকে।
    • Mail server — ব্যবহারকারীদের mailbox (আসা মেইল) ও message queue (পাঠানোর অপেক্ষায় থাকা মেইল)। সার্ভারগুলোর মধ্যে SMTP: পাঠানো সার্ভার = client, গ্রহণকারী = server।

    SMTP (Simple Mail Transfer Protocol)

    • TCP দিয়ে নির্ভরযোগ্যভাবে পাঠায়, port 25।
    • সরাসরি transfer: পাঠানো সার্ভার → গ্রহণকারী সার্ভার।
    • তিন phase: handshaking (greeting) → transfer → closure।
    • Command/response: command = ASCII text, response = status code + phrase।
    • বার্তা অবশ্যই 7-bit ASCII।

    Alice → Bob

    👩 Alice UA→📮 crepes.fr

    ১–২: Alice user agent দিয়ে bob@hamburger.edu-কে মেইল লেখে; UA মেইলটা তার mail server-এ পাঠায়, সেখানে message queue-তে রাখা হয়।

    📮 crepes.frSMTP / TCP :25 →📮 hamburger.edu

    ৩–৪: SMTP-র client অংশ Bob-এর mail server-এর সাথে TCP connection খোলে ও মেইল পাঠায়।

    📮 hamburger.edu📥 mailbox →👨 Bob UA

    ৫–৬: Bob-এর সার্ভার মেইল Bob-এর mailbox-এ রাখে; Bob user agent দিয়ে পড়ে (POP/IMAP/HTTP)।

    S: 220 hamburger.edu C: HELO crepes.fr S: 250 Hello crepes.fr, pleased to meet you C: MAIL FROM: <alice@crepes.fr> S: 250 alice@crepes.fr... Sender ok C: RCPT TO: <bob@hamburger.edu> S: 250 bob@hamburger.edu ... Recipient ok C: DATA S: 354 Enter mail, end with "." on a line by itself C: Do you like ketchup? C: . S: 250 Message accepted for delivery C: QUIT S: 221 hamburger.edu closing connection
    🔒 লক্ষ্য করো

    MAIL FROM:-এ client যা খুশি লিখতে পারে — SMTP কোনো যাচাই করে না! তাই ভুয়া প্রেরকের মেইল (email spoofing / masquerading) এত সহজ।

    ৩) Host-এর DNS query প্রথমে কোথায় যায়?

    Retrieval হলো POP/IMAP-এর কাজ; SMTP পাঠায় (push)।
