    HTML ও HTTP: ওয়েব কীভাবে চলে

    ওয়েব (WWW) প্রায় সবকিছু বদলে দিয়েছে — ব্যাংকিং, কেনাকাটা, শিক্ষা, যোগাযোগ, খবর… এর ভিত্তি দুটো প্রযুক্তি: HTML ও HTTP। ওয়েব = ওয়েবসাইটের সমষ্টি; সাইট = web page; page লেখা হয় HTML-এ; browser HTML interpret করে দেখায়।

    HTML-এর বৈশিষ্ট্য

    • Static document description language
    • অন্য page-এ link ও reference দিয়ে ছবি embed
    • User input যায় form দিয়ে
    • Extension: plugin দিয়ে PDF/ভিডিও; JavaScript/Java দিয়ে dynamic content — যা user-এর সাথে interact করে, browser interface বদলায়, এমনকি client কম্পিউটারের পরিবেশে access পায় (→ নিরাপত্তা ঝুঁকি)
    <i>italics</i> <b>bold</b> <ul><li>first-item</li><li>second-item</li></ul> <a href="web-page-URL">Description</a> ← hyperlink <script>Computer code</script> ← scripting <img src="URL-of-an-image"> ← embedded image

    URL টাইপ করার পর কী হয়

    ১. User browser-এ web address (DNS name) টাইপ করে।

    ২. Browser আগে local DNS cache দেখে; না পেলে DNS server-কে জিজ্ঞেস করে IP বের করে।

    ৩. Web server-এর নির্দিষ্ট port-এ TCP connection — HTTP-র জন্য port 80।

    ৪. HTTP request পাঠায়; server HTML page সহ HTTP response দেয়।

    ৫. Browser page render করে। এক page দেখতে আসলে অনেকগুলো HTTP request লাগতে পারে — প্রতিটা ছবির জন্য আলাদা request। (Browser-এ “View Source” দিয়ে HTML দেখা যায়।)

    HTTP কেন অনিরাপদ

    • ডিফল্টে TCP port 80 দিয়ে, কোনো encryption নেই — সব clear-এ যায়।
    • Packet আটকাতে পারলে attacker ব্যবহারকারীর পাঠানো সব তথ্য পায়, এমনকি MITM হয়ে বদলাতেও পারে।
    • তাই password, credit card নম্বর, Social Security নম্বর পাঠানোর জন্য অনুপযুক্ত।
    • এছাড়া web server-এর পরিচয় নিশ্চিত করা কঠিন — তুমি কি সত্যিই ঠিক সার্ভারের সাথে কথা বলছ, নাকি attacker তার ভান করছে?
    🎯 দুটো সমস্যা → দুটো সমাধান

    (১) Confidentiality/integrity নেই → encrypted channel। (২) Server-এর identity নেই → certificate। HTTPS দুটোই দেয়।

    HTTPS / TLS

    HTTPS = HTTP over SSL। Syntax-এ HTTP-র মতোই, কিন্তু নিচে একটা নিরাপত্তা স্তর — SSL (Secure Socket Layer) বা নতুন TLS (Transport Layer Security)। এরা certificate দিয়ে (১) server-এর identity যাচাই করে, (২) browser ও server-এর মধ্যে encrypted channel তৈরি করে।

    🌐 BrowserClientHello: আমি AES, ChaCha20, SHA-256… পারি →🖥️ Server

    ১. Browser HTTPS session চায় এবং নিজের সমর্থিত cipher ও hash function-এর তালিকা দেয়।

    🌐 Browser← ServerHello: AES + SHA-256 নিলাম🖥️ Server

    ২. Server দুজনেরই সমর্থিত সবচেয়ে শক্তিশালী cipher ও hash বেছে জানায়।

    🌐 Browser← 📜 Certificate (public key সহ)🖥️ Server

    ৩. Server তার certificate পাঠায়, যাতে server-এর public key আছে। ৪. Browser certificate-এর authenticity যাচাই করে।

    🌐 Browser{random R}server public key →🖥️ Server
    private key দিয়ে খোলে

    ৫. Browser একটা random number server-এর public key দিয়ে encrypt করে পাঠায়; server private key দিয়ে খোলে।

    🌐 K🔒 EK(HTTP msg ‖ MAC) ⇄🖥️ K

    ৬. দুজনে R থেকে একই shared secret বানায়। এটা দিয়ে: পরের প্রতিটা বার্তা symmetric encryption (confidentiality) ও MAC (integrity)। এরপর সাধারণ HTTP চলে — প্রতিটা HTTP বার্তায় MAC লাগিয়ে পুরোটা encrypt।

    📖 সংযোগ

    এটা Lecture 4-এর hybrid encryption: ধীর public-key দিয়ে শুধু key বিনিময়, তারপর দ্রুত symmetric। আর Lecture 5-এর certificate + MAC — সব একসাথে!

    Digital Certificate ও Hierarchy

    Certificate server-এর public key দেয় এবং সাইটের identity প্রমাণ করে। এটা একটা বিশ্বস্ত তৃতীয় পক্ষ — Certificate Authority (CA) — তার private key দিয়ে সই করে। সাইটের মালিক CA-কে Certificate Signing Request (CSR) ও ফি দেয়; CA পরিচয় ও domain-এর মালিকানা যাচাই করে সই করে।

    🎯 এক লাইনে

    Web server certificate = issuer (CA)-র একটা attestation: subject (সাইটের মালিক প্রতিষ্ঠান) + domain name + server-এর public key একসাথে বাঁধা।

    Certificate hierarchy (Chain of trust)

    CA-র নিজের পরিচয় কে যাচাই করবে? আরেকটা উচ্চতর CA-র সই করা certificate → intermediate CA-দের hierarchy। শীর্ষে root certificate — এর উপরে কেউ নেই, তাই এটা self-signed (issuer = subject), নিজের বৈধতা নিজেই ঘোষণা করে। Root certificate হলো chain of trust-এর anchor point; OS বা browser এদের সুরক্ষিত ফাইলে আগে থেকেই রাখে।

    🏛️ Root CA (self-signed, browser-এ আগে থেকে আছে) ← trust anchor │ সই করে 🏢 Intermediate CA │ সই করে 🌐 www.paypal.com (server certificate)
    🧪 Browser-এর মতো certificate যাচাই করো

    EV Certificate, CRL ও Usability

    Extended Validation (EV)

    কিছু CA শুধু domain validation করে — certificate-এর domain আবেদনকারীর মালিকানায় কি না। আরও কঠোরভাবে পরিচয় যাচাইয়ের জন্য extended validation certificate — শুধু সেই CA দিতে পারে যারা CA/Browser Forum-এর কঠোর মানদণ্ডের audit পাস করেছে। EV certificate-এর CA field-এ তা উল্লেখ থাকে।

    মেয়াদ ও বাতিল (Revocation)

    • প্রতিটা certificate-এর validity period আছে।
    • মেয়াদের আগেই অবৈধ হতে পারে — private key ফাঁস বা সাইট পরিচালনাকারী প্রতিষ্ঠান বদল।
    • তখন CA serial number Certificate Revocation List (CRL)-এ যোগ করে; CRL CA-র সই করা ও revocation site-এ প্রকাশিত (URL certificate-এই থাকে)।
    🎯 Certificate পুরোপুরি যাচাই = ৪ কাজ
    1. Certificate-এর সই যাচাই
    2. CRL download
    3. CRL-এর সই যাচাই
    4. Serial number CRL-এ আছে কি না দেখা

    Usability

    পুরো ব্যবস্থা নির্ভর করে user browser-এর দেখানো তথ্য বুঝে সিদ্ধান্ত নেয় কি না তার উপর — padlock icon, address bar-এ সবুজ পটভূমিতে প্রতিষ্ঠানের নাম (EV), ক্লিক করলে certificate-এর সারাংশ।

    Semantic Attack

    Certificate syntactically নিখুঁত প্রযুক্তি, কিন্তু semantic আক্রমণে দুর্বল। Bruce Schneier: “যে আক্রমণ লক্ষ্য করে আমরা মানুষেরা কীভাবে content-এ অর্থ আরোপ করি… সরাসরি human/computer interface-কে — ইন্টারনেটের সবচেয়ে অনিরাপদ interface।”

    ১. 0ntest.com domain কেনো (শূন্য 0, ইংরেজি O নয়)।

    ২. 0ntest.com-এর জন্য বৈধ digital certificate কেনো — CA শুধু দেখে domain তোমার কি না, আর সেটা সত্যিই তোমার!

    ৩. ontest.com-এর হুবহু নকল সাইট বানাও।

    ৪. User-কে 0ntest.com-এ পাঠাও। Browser certificate বৈধ দেখাবে — 🔒 padlock সহ! সাধারণ মানুষ কি পার্থক্য ধরতে পারবে?

    🧪 Look-alike domain detector

    চেষ্টা করো: paypa1.com, rnicrosoft.com (r+n = m), gooogle.com, bkash.com

    Dynamic HTML, DOM ও JavaScript

    শুধু fixed content-এর page = static; user-এর interaction বা সময়ের সাথে বদলায় এমন page = dynamic। এজন্য scripting language — অ্যাপ্লিকেশনের (browser) ভেতরে চলা নির্দেশনা; লেখা program = script।

    Document Object Model (DOM)

    Web page-এর content-কে সংগঠিতভাবে প্রকাশের উপায়। Object-oriented পদ্ধতিতে tag ও element-গুলো parent-child সম্পর্কের object → DOM tree। Script tree traverse করে page-এর যেকোনো object access ও পরিবর্তন করতে পারে।

    document └─ html ├─ head ─ title ─ "My bank" └─ body ├─ h1 ─ "Welcome" ├─ form#login ─ input[name=user], input[name=pwd] └─ img[src=logo.png]

    JavaScript

    • ১৯৯৫-এ এসেছে, এখন সব প্রধান browser সমর্থন করে; <script>…</script> ট্যাগে লেখা।
    • Function declare ও argument পাস; C-এর মতো for, while, if/else, switch।
    • Event handling — ক্লিক, mouse-over: <img src="picture.gif" onMouseOver="javascript:hello()"> — ছবির উপর মাউস নিলেই hello() চলে, “Hello world!” pop-up।
    • DOM tree access করে page-এর content dynamically বদলাতে পারে।
    🔒 কেন এটা সিকিউরিটির বিষয়

    JavaScript DOM-এর সবকিছু — form-এ টাইপ করা password, এমনকি cookie (document.cookie) — পড়তে পারে। তাই অন্য কেউ যদি তোমার page-এ নিজের script ঢুকিয়ে দিতে পারে, সে সব পায় → XSS (Lecture 26)। আর mouse-over event দিয়ে click-jacking (Lecture 25)।

    HTTP Session ও Hidden Field

    HTTP stateless — প্রতিটা নতুন page request সার্ভারের কাছে নতুন সাক্ষাৎ। কিন্তু login, shopping cart-এর জন্য user-কে মনে রাখা দরকার। Session = একাধিক page জুড়ে টিকে থাকা ভিজিটরের তথ্য। তিন উপায়:

    1. GET বা POST variable দিয়ে session তথ্য পাঠানো
    2. Cookie (Lecture 25)
    3. Server-side session variable (Lecture 25)
    ⚠️ Session = অত্যন্ত সংবেদনশীল

    ব্যাংক, ক্রেডিট কার্ড, স্বাস্থ্য রেকর্ডে consistent identity এটাই দেয়। Session hijacking = যেকোনো পরিস্থিতি যেখানে attacker user-এর session তথ্য পেয়ে তার পরিচয়ে সাইটে authenticate করে।

    GET/POST দিয়ে session — hidden field

    <form method="POST" action="cart.php"> <input type="hidden" name="sessionid" value="7456"> ... </form>

    User দেখে না, কিন্তু প্রতিবার page বদলালে এই তথ্য server-এ যায়; server একই hidden কোড দিয়ে পরের page বানায়।

    • দুর্বলতা: HTTP unencrypted → MITM-এ খুব দুর্বল। GET/POST variable পেলেই attacker session hijack করে user সেজে যায়।
    • সমাধান: session-এর সাথে অবশ্যই HTTPS।
    💡 “Hidden” মানে গোপন নয়

    যেকেউ “View Source” বা DevTools খুলে hidden field দেখতে ও বদলাতে পারে। পুরনো কিছু শপিং সাইট দাম hidden field-এ রাখত — user দাম ১০০০ থেকে ১ করে দিলেই হলো!

    রিভিশন কুইজ

    ১) HTTPS-এ session শেষে বার্তা encrypt হয় কী দিয়ে?
    Public key শুধু random number পাঠাতে; বাকিটা দ্রুত symmetric।
    ২) Root certificate-এর বৈশিষ্ট্য কোনটা?
    উপরে কেউ নেই, তাই নিজেই সই করে।
    ৩) 0ntest.com-এর বৈধ certificate থাকা সত্ত্বেও user প্রতারিত হয় — এটা কোন আক্রমণ?
    মানুষ কীভাবে অর্থ বোঝে তাকেই লক্ষ্য।
    ৪) Certificate মেয়াদের আগেই কেন বাতিল হতে পারে?
    তখন serial number CRL-এ যায়।
