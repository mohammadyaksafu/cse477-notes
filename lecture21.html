    LECTURE 21

    Network Attacks II — Session Hijacking, DoS/DDoS, DNS Poisoning

    TCP 3-way handshake থেকে TCP sequence prediction দিয়ে session hijacking; DoS-এর তিন রূপ — Ping flood, Smurf, SYN flood (ও SYN cookie); বটনেট দিয়ে DDoS; আর DNS cache poisoning ও প্রতিকার।

    SYN · SYN-ACK · ACKSequence predictionPing flood · SmurfSYN flood · SYN cookieBotnetDNS cache poisoning

    TCP 3-way Handshake

    💻 ClientSYN, seq = x →🖥️ Server

    ১. SYN: Client একটা initial sequence number x বেছে connection চায়।

    💻 Client← SYN-ACK, seq = y, ack = x+1🖥️ Server
    half-open state মনে রাখে

    ২. SYN-ACK: Server নিজের sequence number y বেছে x+1 acknowledge করে, আর এই অর্ধ-খোলা connection-এর তথ্য memory-তে রাখে।

    💻 ClientACK, ack = y+1 →🖥️ Server ✅

    ৩. ACK: Client y+1 acknowledge করে। Connection established। যে y+1 জানে, server তাকেই client মনে করে!

    🎯 মূল কথা

    এই লেকচারের দুটো আক্রমণ handshake-এর দুই দুর্বলতা ব্যবহার করে: sequence prediction → ধাপ ৩-এর y+1 আন্দাজ করা; SYN flood → ধাপ ২-এর memory ভরিয়ে ফেলা।

    TCP Session Hijacking ও Sequence Prediction

    Session = server যে client-এর connection-এর state রাখে (কোন বার্তা গেল, কী কাজ হলো)। TCP session hijacking = সেই নেটওয়ার্ক session-এর নিয়ন্ত্রণ নিয়ে নেওয়ার চেষ্টা। Attacker-এর অবস্থান ও জ্ঞানের উপর এর কয়েক রকম রূপ আছে।

    TCP sequence prediction = server-এর initial sequence number আন্দাজ করে একটা spoofed TCP session তৈরি।

    • পুরনো TCP stack: প্রতিবার ১ করে বাড়ানো সরল counter — কোনো randomness নেই, তাই পরেরটা আন্দাজ করা খুবই সহজ।
    • আধুনিক stack: pseudo-random number generator — কঠিন, কিন্তু অসম্ভব নয়।

    আক্রমণের ধাপ

    😈 Attacker💥 DoS →💻 Victim client

    ১. Victim client-এর উপর DoS — যাতে সে হস্তক্ষেপ (RST পাঠানো) করতে না পারে।

    😈 Attacker
    src = victim IP    SYN →🖥️ Server

    ২. Server-কে SYN পাঠায়, source IP spoof করে victim-এর।

    🖥️ ServerSYN-ACK (seq=y) → ✖💻 Victim (অচল)

    ৩. Server-এর SYN-ACK victim-এর কাছে যায় — attacker দেখতে পায় না, victim DoS-এ থাকায় সাড়াও দেয় না।

    😈 Attacker
    src = victim IP    ACK, ack = আন্দাজ y+1 →🖥️ Server ✅

    ৪. একটু অপেক্ষা করে আন্দাজ করা sequence number দিয়ে ACK — handshake শেষ। এখন attacker victim সেজে request পাঠাতে পারে।

    🧪 Sequence number আন্দাজ করো

    প্রতিকার

    • Encryption ও authentication — network layer-এ (IPsec) অথবা application layer-এ পুরো session encrypt করে এমন protocol।
    • সাইটগুলো যেন secure authentication দিয়ে শুরু করে পরে unencrypted-এ না নামে — এতে efficiency-র জন্য security বিসর্জন হয়।

    DoS: Ping Flood ও Smurf

    Bandwidth সীমিত, তাই একটা সার্ভার যতগুলো connection রাখতে পারে তাও সীমিত। Bandwidth বা প্রসেসর শেষ হলে নতুন connection drop হয়। মেশিন/সফটওয়্যারকে তার মৌলিক কাজ করতে অক্ষম করার যেকোনো আক্রমণ = Denial-of-Service (DoS)। Attacker-এর পরিচয় লুকাতে ও প্রতিকার কঠিন করতে প্রায়ই source IP spoof করা হয়।

    তিন ধরন: ICMP আক্রমণ (Ping flood, Smurf) ও SYN flood।

    Ping Flood

    শক্তিশালী মেশিন দুর্বল সার্ভারে বিপুল ICMP echo request পাঠায়। দুটো শর্ত পূরণ হলে victim ডুবে যায় ও বৈধ connection drop করে:

    1. Attacker যত request বানাতে পারে, victim তত প্রসেস করতে পারে না;
    2. Victim-এর সব request গ্রহণ করার মতো যথেষ্ট bandwidth আছে।

    Smurf (Directed Broadcast) Attack

    কিছু implementation broadcast address-এ পাঠানো ping-এরও উত্তর দেয়। Attacker:

    😈 Attackerping → 192.168.1.255
    src = victim IP    🏢 Amplifier LAN

    ১. Source address-এ victim-এর IP বসিয়ে একটা ping পাঠায় একটা নেটওয়ার্কের broadcast address-এ (Smurf amplifier)।

    🏢 ১০০টা host১০০ × ECHO reply →🎯 Victim

    ২. LAN-এর প্রতিটা host victim-কে উত্তর দেয় — একটা packet → শত শত reply। Amplification! আগের দুটো শর্ত পূরণ হলে victim ডুবে যায়।

    🧪 Amplification হিসাব

    Smurf প্রতিকার

    • Host ও router যেন broadcast request উপেক্ষা করে।
    • Router যেন broadcast address-এ পাঠানো packet forward না করে (নইলে নেটওয়ার্ক নিজেই amplifier)।
    • দুর্বল সার্ভার হলে ping সম্পূর্ণ উপেক্ষা করা ভালো (ping flood ঠেকাতে)।

    SYN Flood ও SYN Cookie

    Attacker প্রচুর SYN পাঠায়, SYN/ACK উপেক্ষা করে, কখনো ACK পাঠায় না। সাধারণত random spoofed source দেয়, তাই SYN/ACK random IP-তে যায়। Server-এর memory ভরে যায় half-open connection-এর sequence number দিয়ে, যেগুলোর ACK কখনো আসবে না → বৈধ connection request জায়গা পায় না।

    🧪 SYN flood simulator — server-এর backlog queue (১৬ স্লট)

    SYN Cookie

    Handshake শেষ না হওয়া পর্যন্ত server client-এর state আসলে রাখেই না — state-টা sequence number-এর ভেতরেই ঢুকিয়ে দেয়:

    SYN এলে: y = H(src IP, src port, dst IP, dst port, counter, SECRET) → SYN-ACK-এ seq = y পাঠাও, কিছু মনে রেখো না ACK এলে: ack − 1 আবার হিসাব করে মেলাও → মিললে তবেই connection তৈরি
    • H হতে পারে one-way hash function; SECRET শুধু server জানে।
    • Sequence number আন্দাজ করা কঠিন হতে হবে।

    SYN cookie-র সীমাবদ্ধতা

    • Windows গ্রহণ করেনি; কয়েকটা Linux distribution-এ আছে।
    • প্রধান সমস্যা: সাধারণত TCP options field ব্যবহার করতে দেয় না — কারণ এই তথ্য সাধারণত SYN queue entry-র সাথে রাখা হয়।
    • নতুন Linux implementation option তথ্য TCP packet-এর timestamp field-এ encode করে এই সমস্যা কমানোর চেষ্টা করে।

    Distributed DoS (DDoS)

    একাধিক (শত/হাজার) আক্রমণকারী মেশিন দিয়ে একটা সাইটে ট্রাফিক পাঠিয়ে DoS = DDoS। Yahoo!, Amazon, Google বারবার শিকার হয়েছে। প্রায়ই botnet ব্যবহার হয় — দূর থেকে নিয়ন্ত্রণযোগ্য, আপোষকৃত মেশিনের বিশাল নেটওয়ার্ক।

    😈 Attacker │ command ┌───────┼───────┐ 🖥️ C&C 🖥️ C&C 🖥️ C&C ← handler / master ╱ │ ╲ ╱ │ ╲ ╱ │ ╲ 🤖 🤖 🤖 🤖 🤖 🤖 🤖 🤖 🤖 ← zombie/bot (আক্রান্ত PC, IoT ক্যামেরা…) ╲ ╲ ╲ │ ╱ ╱ ╱ 🎯 Victim server

    প্রতিকার

    • তত্ত্বে DDoS সম্পূর্ণ দূর করা অসম্ভব — server-এর bandwidth সবসময় সীমিত।
    • তবু ঝুঁকি কমানো যায়: আসা ট্রাফিক বিশ্লেষণ করে যেসব উৎস অতিরিক্ত bandwidth খাচ্ছে তাদের packet drop।
    • কিন্তু IP spoofing bot-দের পরিচয় লুকিয়ে ও অসামঞ্জস্যপূর্ণ উৎস দেখিয়ে প্রতিরোধ কঠিন করে।
    💡 বাস্তব উদাহরণ

    ২০১৬-র Mirai botnet লাখো IoT ক্যামেরা/রাউটার (ডিফল্ট password-এর) দিয়ে DNS provider Dyn-কে আক্রমণ করে — Twitter, Netflix, Reddit কয়েক ঘণ্টা অচল ছিল।

    DNS Cache Poisoning

    Lecture 19-এ দেখেছি local DNS (LDNS) server উত্তর cache করে, আর DNS-এ মূলত কোনো authentication নেই — LDNS শুধু দেখে উত্তরের query ID (16-bit) ও port মিলছে কি না। Attacker এই সুযোগে ভুয়া উত্তর cache-এ ঢোকায়।

    😈 Attacker“www.bank.com কোথায়?” →🗄️ LDNS

    ১. Attacker LDNS-কে এমন নাম জিজ্ঞেস করে যা cache-এ নেই। LDNS authoritative server-কে প্রশ্ন করে (query ID = কোনো একটা সংখ্যা)।

    😈 Attackerশত শত ভুয়া উত্তর
    “bank.com = 6.6.6.6”, ID = 1, 2, 3…    🗄️ LDNS

    ২. আসল উত্তর আসার আগেই attacker authoritative server সেজে অনেক ভুয়া উত্তর পাঠায়, প্রতিটায় আলাদা ID আন্দাজ করে।

    🗄️ LDNS
    cache: bank.com → 6.6.6.6 ☠️

    ৩. কোনো একটার ID মিলে গেলে LDNS সেটা বিশ্বাস করে cache-এ রাখে; পরে আসা আসল উত্তর বাতিল।

    👥 ISP-র সব গ্রাহকbank.com →🎣 6.6.6.6 (ভুয়া সাইট)

    ৪. TTL শেষ না হওয়া পর্যন্ত ওই ISP-র সব ব্যবহারকারী ঠিক URL টাইপ করেও ভুয়া সাইটে যায় → phishing, malware।

    প্রতিকার

    • বেশিরভাগ আক্রমণ লক্ষ্য করে ISP-র LDNS-কে, authoritative server-কে নয়।
    • আগে LDNS বাইরের সবার জন্য খোলা থাকত; ২০০৮ থেকে বেশিরভাগ LDNS শুধু নিজের internal network-এর request নেয় → ISP-র বাইরে থেকে poisoning বন্ধ।
    • কিন্তু নেটওয়ার্কের ভেতর থেকে আক্রমণের সম্ভাবনা থেকেই যায়; অন্য কৌশলও আছে (source port randomization, DNSSEC), তবু poisoning-এর সম্ভাবনা এখনো আছে।

    রিভিশন কুইজ

    ১) TCP sequence prediction আক্রমণের শুরুতে attacker victim client-এর উপর DoS চালায় কেন?
    Victim অপ্রত্যাশিত SYN-ACK পেলে RST পাঠিয়ে connection ভেঙে দিত।
    ২) Spoofed source দিয়ে broadcast address-এ ping — কোন আক্রমণ?
    Directed broadcast + amplification = Smurf।
    ৩) SYN cookie-তে server half-open connection-এর state কোথায় রাখে?
    Server কিছু মনে রাখে না; ACK এলে আবার হিসাব করে মেলায়।
    ৪) ২০০৮-এর পর DNS cache poisoning কমাতে LDNS-এ কী করা হয়?
    বাইরে থেকে poisoning-এর চেষ্টা বন্ধ হয়।
