    Web Security II — Cookie, Session Hijacking, Phishing ও Mobile Code

    Cookie দিয়ে HTTP Session

    Cookie = কোনো নির্দিষ্ট server-এর সাথে যুক্ত, client-এর কম্পিউটারে রাখা ছোট তথ্য। Server HTTP response-এর Set-Cookie header দিয়ে সেট করে; user আবার সাইটে এলে cookie অপরিবর্তিত অবস্থায় ফেরত যায় — server user-কে “মনে রাখে”।

    Set-Cookie: SESSIONID=8f3a9c…; Domain=.paypal.com; Path=/; Expires=Wed, 01 Jan 2027 00:00:00 GMT; Secure; HttpOnly
    অংশঅর্থ
    Name = ContentCookie-র key-value pair
    Domain .paypal.comএই top-level domain ও সব subdomain-এ বৈধ
    Path /সাইটের root directory-তে প্রযোজ্য (না দিলে ডিফল্ট root)
    Send for / Secure“Any type of connection” = secure নয়; Secure দিলে শুধু HTTPS-এ যায়
    Expiresকখন নিজে মুছবে; না দিলে browser বন্ধ করলেই মুছে যায় (session cookie)

    Cookie Property: Domain, Path, Secure, HttpOnly

    Domain নিয়ম

    • শুধু ওই domain-এর host-রাই সেই domain-এর cookie সেট করতে পারে।
    • Subdomain উপরের স্তরের domain-এর জন্য cookie সেট করতে পারে, উল্টোটা নয়।
    • Subdomain উপরের domain-এর cookie পড়তে পারে, উল্টোটা নয়: mail.example.com পড়তে পারে example.com ও mail.example.com-এর cookie; example.com পারে না mail.example.com-এর।
    • Host শুধু এক স্তর উপরের domain-এর জন্য সেট করতে পারে: one.mail.example.com .example.com-এর cookie পড়তে পারে, কিন্তু সেট করতে পারে না।
    🧪 Cookie domain checker (স্লাইডের নিয়ম অনুযায়ী)

    Path, Secure ও HttpOnly

    • Client স্বয়ংক্রিয়ভাবে ওই domain ও path-এর সব cookie HTTP request-এর Cookie: field-এ পাঠায়।
    • Cookie DOM দিয়ে accessible — তাই অনেক scripting language পড়তে পারে। JavaScript cookie-কে DOM-এ রাখা সাধারণ string হিসেবে দেখে (document.cookie); অনেক ভাষার নিজস্ব cookie API আছে।
    • এসব property browser সামলায়, OS নয় — প্রতিটা browser-এর আলাদা cookie সেট।

    Cookie security

    • Cookie-তে সংবেদনশীল তথ্য unencrypted রাখা বিপজ্জনক — ওই কম্পিউটারের user-রা পড়তে পারে।
    • Encrypt থাকলেও কারো cookie পেলেই তার session নেওয়া যায় → cookie-কে login তথ্যের মতোই রক্ষা করো।
    • Expiration ভালো প্রতিরোধ, তবু নিয়মিত cookie মুছে ফেলা উচিত।
    • এছাড়া privacy সমস্যা (শেষ অংশে)।

    Server-side Session

    User-এর তথ্য server-এই রাখা — user-এর কম্পিউটার আক্রান্ত হলেই web session আক্রান্ত হয় না। E-commerce-এর shopping cart-এ বহুল ব্যবহৃত।

    • Server একটা session ID / session token দেয় — session-এর unique identifier।
    • Client-এ token রাখা হয় আগের দুই উপায়ের একটায় (GET/POST variable বা cookie); প্রতিবার page বদলালে token server-এ যায়, server তথ্য বের করে।
    • Session ID আন্দাজ করা কঠিন হতে হবে → random number generator বা MAC দিয়ে বানানো।
    • Client কম্পিউটার আক্রান্ত হলে attacker শুধু একটা পুরনো session ID পায়, যা সম্ভবত ততক্ষণে expired।
    📖 উপমা

    Cookie-তে সব তথ্য রাখা = পকেটে টাকার বান্ডিল নিয়ে ঘোরা। Server-side session = টাকা লকারে রেখে শুধু লকারের টোকেন পকেটে — টোকেন হারালেও তাড়াতাড়ি বাতিল করা যায়।

    HTTP Session Hijacking ও প্রতিরক্ষা

    TCP session hijacking-এর মতো HTTP session-ও দখল করা যায়। বিশেষত বিপজ্জনক যখন শুরুতে শক্তিশালী authentication, কিন্তু পরে যোগাযোগ unencrypted। Attacker-কে (১) যোগাযোগ intercept করতে হয়, এবং (২) session রক্ষার যে ব্যবস্থা (token) তা নকল করতে হয়।

    • Packet sniffer দিয়ে victim-এর session ID, cookie-র token বা GET/POST variable জানা যায়।
    • বৈধ server-side token পুনর্গঠন বা client-side token নকল করতে পারলেই user সেজে যায়।
    • তাই প্রথম প্রতিরক্ষা: packet sniffer ও TCP session hijacking থেকে সুরক্ষা।

    Phishing ও URL Obfuscation

    Phishing = সংবেদনশীল তথ্য প্রতারণা করে হাতানোর জন্য বানানো ভুয়া web page। সাধারণত spam ইমেইল দিয়ে user-কে সেখানে নেওয়া হয়। সবচেয়ে বেশি লক্ষ্য: আর্থিক সেবা (Citibank), payment (PayPal), নিলাম (eBay)। ২০০৯-এ প্রতি মাসে ~৪৫,০০০ unique phishing সাইট (APWG)।

    • Phishing নির্ভর করে user যে page ভালো করে দেখবে না তার উপর — হুবহু নকল বানানো কঠিন।
    • DNS cache poisoning না হলে address bar-এ এক নজর দিলেই ধরা যায়; source code দেখেও প্রমাণ মেলে।
    • Browser-এর জনপ্রিয় প্রতিরোধ: নিয়মিত আপডেট হওয়া phishing সাইটের blacklist — সেখানে গেলে সতর্কবার্তা।

    URL obfuscation

    • সাধারণ বানান ভুল (paypa1.com) চোখ এড়িয়ে যায়।
    • HTML ইমেইলে লিংকের দেখানো লেখা আর আসল গন্তব্য আলাদা:
    <a href="http://www.evilsite.com/">https://www.mybank.com/wiki/Login</a> └──── আসল গন্তব্য ────┘ └──────── user যা দেখে ────────┘

    Homograph (Unicode) attack

    বহু ভাষায় domain সমর্থনের জন্য URL-এ Unicode অক্ষর চলে। অনেক অক্ষরের Unicode মান আলাদা কিন্তু দেখতে হুবহু এক। বিখ্যাত উদাহরণ: www.paypal.com রেজিস্টার করা হয়েছিল Cyrillic р (U+0440) দিয়ে, ASCII p (U+0070)-র বদলে। বৈধ certificate থাকলে এটা semantic attack-এর নিখুঁত রূপ।

    🧪 দুটো “paypal” — একই দেখায়?
    একটা বাটনে ক্লিক করো — প্রতিটা অক্ষরের code point দেখাবে।

    Click-jacking

    User-এর মাউস ক্লিক এমনভাবে ব্যবহার করা যা user চায়নি। সহজ উদাহরণ — লিংক দেখতে www.trustedsite.com, কিন্তু ক্লিক করলে অন্যত্র:

    <a onMouseUp="window.open('http://www.evilsite.com/')" href="http://www.trustedsite.com/">Trust me!</a>

    এমনকি নিরাপত্তার মিথ্যা অনুভূতি দেয় — hover করলে status bar-এ trustedsite.com-ই দেখায়!

    • শুধু ক্লিক নয় — onMouseOver-এর মতো event-এ মাউস নাড়ালেই কাজ হয়ে যায়।
    • Click fraud: বিজ্ঞাপনদাতারা click-through সংখ্যা অনুযায়ী টাকা দেয় → click-jacking দিয়ে user-কে অনিচ্ছায় বিজ্ঞাপনে ক্লিক করিয়ে আয় বাড়ানো।
    💡 আধুনিক রূপ

    অদৃশ্য (opacity 0) iframe-এ আসল সাইটের “Delete account” বাটন, তার ঠিক উপরে দৃশ্যমান “Win iPhone!” বাটন — তুমি ক্লিক করো পুরস্কারে, আসলে চাপো delete-এ। প্রতিকার: সাইট X-Frame-Options / CSP frame-ancestors দিয়ে frame-এ ঢোকা নিষেধ করে।

    Sandboxing, Flash ও Mobile Code

    Sandbox = অন্য অ্যাপ্লিকেশনের ভেতরে চলা অ্যাপ/script-এর সীমিত অধিকার — যেমন শুধু নির্দিষ্ট ফাইল ও ডিভাইসে access। Google Chrome প্রতিটা নতুন tab আলাদা process-এ চালায় → OS স্তরে প্রতিটা tab sandboxed; এক tab-এর দুর্বলতা দিয়ে অন্য tab-এর content পাওয়া যায় না।

    Adobe Flash ও media player

    Embedded media player-এ ত্রুটি থাকলে ক্ষতিকর media ফাইল browser-এর sandbox ভেঙে victim-এর মেশিনে কোড চালাতে পারে — streaming প্রযুক্তিতে বারবারের সমস্যা। Flash প্রায় সর্বত্র ছিল (বিজ্ঞাপন, interactive content) → সবসময় সর্বশেষ (patched) version ব্যবহার। (Flash ২০২০-এ বন্ধ হয়েছে।)

    Mobile code

    নেটওয়ার্কে পাঠানো, গন্তব্যে চলা executable program — JavaScript, ActiveX, Java plugin, integrated JVM।

    ActiveX-এর বিপদ

    • Signed control অনুমতি চায়; অনুমোদন দিলে user-এর সমান অধিকারে চলে।
    • “Always trust content from …” চেকবক্স = ওই publisher-এর সব control স্বয়ংক্রিয় গ্রহণ — সম্ভবত খারাপ ধারণা।
    • Trusted publisher-এর তালিকা Windows registry-তে; ক্ষতিকর control registry বদলে নিজের publisher-কে trusted করে ফেলতে পারে → ভবিষ্যতে সব prompt ছাড়াই চলে।
    • Unsigned control reject করলেও সেটা আগেই temp folder-এ download হয়ে থাকে — চলে না, কিন্তু মোছাও হয় না।

    Privacy Attack: Third-party Cookie

    Adware/spyware ছাড়াও cookie নির্দিষ্ট privacy সমস্যা তৈরি করে। Server HTTP response দিয়ে cookie সেট করে — তাই কোনো সাইটে অন্য সাইটে host করা ছবি embed থাকলে, ছবির সাইটও তোমার মেশিনে cookie সেট করতে পারে → third-party cookie।

    তুমি যাও news.com → পেজে <img src="https://ads.tracker.com/pixel.gif"> → tracker.com cookie সেট: uid=42 তুমি যাও shop.com → একই pixel → browser পাঠায় Cookie: uid=42 তুমি যাও health.com → আবার uid=42 ⇒ tracker.com জানে: uid 42 খবর পড়ে, জুতা খোঁজে, ডায়াবেটিস নিয়ে পড়ে 😟
    • মূলত বিজ্ঞাপনদাতারা অনেক সাইট জুড়ে user track ও পরিসংখ্যান সংগ্রহে ব্যবহার করে — user-এর অজান্তে ও সম্মতি ছাড়া, তাই অনেকে privacy লঙ্ঘন মনে করে।
    • Third-party cookie block করলেও tracking পুরো বন্ধ হয় না — বিজ্ঞাপন নেটওয়ার্ক অংশগ্রহণকারী সাইটগুলোর একাধিক domain নামে image server রাখতে পারে।

    Browser-এর privacy ফিচার

    • Cookie কতদিন থাকবে ও third-party cookie অনুমোদিত কি না — policy।
    • History ও cached ফাইল স্বয়ংক্রিয় মুছে ফেলা।
    • Anonymity-র জন্য proxy server।
    • Private browsing mode — cookie ও history সংরক্ষণ হয় না।

    রিভিশন কুইজ

    ১) কোন flag দিলে JavaScript (document.cookie) cookie পড়তে পারে না?
    HttpOnly → script access বন্ধ; কিন্তু browser request-এ পাঠাবেই।
    ২) example.com কি mail.example.com-এর cookie পড়তে পারে?
    উপরের দিকে পড়া চলে, নিচের দিকে নয়।
    ৩) Session token-কে client-এর IP-র সাথে বাঁধা, token ঘন ঘন বদলানো — মূলত কী ঠেকাতে?
    চুরি করা বা পুরনো token অকেজো হয়।
    ৪) www.paypal.com-এ ‘p’-এর জায়গায় Cyrillic ‘р’ (U+0440) — কোন আক্রমণ?
    দেখতে একই, Unicode মান আলাদা।
